# 测试5「税前利润识别不到」根因与修复报告

**日期**：2026-09-03
**范围**：供应商 Z-Score 自动化（`zscore-web/` + `zscore_pipeline/`）
**故障单**：「最新测试的测试5用ai识别也未识别到税前利润这一栏」

## 一、问题与诊断

测试5（supplier `c7ea26ed-f2d5-4296-8c20-83e2dde9f038`，
run `646459a6-8456-415c-9fdb-6798e2539287`）的 Z 值计算缺 `profit_before_tax` 与 `ebit`，
notes 明确标注「X3 缺失 → 未计入 Z」。两条补救路径都失效：

- **流水线路径**：`glm_ocr` 方法偶发漏读关键行
- **前端 AI 补全路径**（点「AI 识别」按钮）：始终返回 null

经过数据库直查 + 真实 OCR 复现 + pdftoppm 实测，确认问题并非单点，而是 **三个独立 bug 叠加**。

## 二、根因

### 根因 1（最致命）：`pdftoppm -W/-H` 单位用错

`lib/ai-client.ts::pdfToCroppedBase64` 用 `pageW/pageH`（pdfinfo 报的**点**，72 DPI）
直接当裁切尺寸传给 `pdftoppm`。但 poppler 在带 `-r` 时把 `-x/-y/-W/-H` 解释为**输出像素**。

实测（A4 595×842 pt，DPI 200）：

| 调用方式 | 输出像素 |
|---|---|
| `-r 200`（无裁切） | 1654 × 2339 ✓ 整页 |
| `-r 200 -x 0 -y 0 -W 595 -H 842`（原代码 FULL_PAGE 用法） | **595 × 842** ✗ 仅左上角 ~36%×36% |
| `-r 200 -x 0 -y 0 -W 1654 -H 2339`（正确的输出像素） | 1654 × 2339 ✓ |

结果：测试5 的「FULL_PAGE」整页渲染实际只输出 595×842 像素的图像（A4 整页的左上 ~36%×36%），
**整张利润表的下半部分（含「三、利润总额」行）被截断**。
GLM-4V-Flash 看到的是只剩 4 行的利润表顶部 → 返回 `value: null` 并附 `ev: "三、利润总额"`（凭上下文推断标签）。

### 根因 2：split 模式永远裁第 1 页 + 假设「横向三表并排」

测试5 的 PDF 是 **A4 纵向 2 页、每页一张表**（第 1 页资产负债表、第 2 页利润表），
但 `callMultimodalSplitModel` 写死了：

- `-l 1`（只取第 1 页）
- `BS_CROP`/`IS_CROP` 是按 960×540pt 横向三表并排算的固定百分比

裁第 1 页 → 「利润表」裁到的是资产负债表的中间竖条 → 模型看到的全是 BS 行 → 「三、利润总额」自然不存在。

> 历史联想：DT 基准测试碰巧用的是「横向三表并排」，所以旧行为没爆。

### 根因 3：IS prompt 误导模型把「三、利润总额」填进 `ebit`

`ai-prompts.ts::IS_FIELDS = ["revenue","ebit"]` 只有两项；`buildIsSystemPrompt` 还在硬规则里写：

> `ebit = 小企业 02 表无"息税前利润"行——直接用"三、利润总额"（第 30 行）。`

照此 prompt，模型把 `三、利润总额 = 9,433,656.95` 写进了 `ebit`，
**而 `profit_before_tax` 永远为 null**（因为模型根本没被问到这一字段）。

`callMultimodalIs` 的默认白名单 `["revenue","ebit"]` 与 `IS_FIELDS` 脱钩；
`callMultimodalSplitModel` 只下发"实际缺失"的字段子集（只缺 ebit 时 `isNeeded=["ebit"]`），
进一步放大了 bug。

### 附带的次要问题

- `ai-analyze` 路由的恒等推导从**已过滤的** `finalSuggestions` 找 PBT，
  只请求 `ebit` 时 PBT 已被过滤掉 → 推导永远失效
- Python 流水线 `glm_ocr` 漏读关键字段后**完全无兜底**，
  实测同源 PDF 连跑 3 次「三、利润总额」行仅 1 次读出（漏读率 ≈ 2/3）

## 三、修复方案

### 修复 1：`pdftoppm` 裁切单位换算（核心）

`lib/ai-client.ts::pdfToCroppedBase64` 改为：

```ts
const pxW = Math.round((pageW * dpi) / 72);
const pxH = Math.round((pageH * dpi) / 72);
const x = Math.max(0, Math.round(crop.x_pct * pxW));
const y = Math.max(0, Math.round(crop.y_pct * pxH));
const w = Math.max(1, Math.round(crop.w_pct * pxW));
const h = Math.max(1, Math.round(crop.h_pct * pxH));
```

`pageW/pageH`（点）先 × `dpi/72` 换算到输出像素，再乘百分比。
**横向版面与纵向版面从此都按真实输出像素裁切**，不再有歧义。

### 修复 2：版面自适应 + 页码定位

新增 `getPdfMeta()`、`classifyStatementPage()`、`detectStatementPages()`：

```text
if (pageCount >= 2 && pageH > pageW) {   // 纵向多页
  layout = "portrait-page"
  {bsPage, isPage} = detectStatementPages()
  // 整页渲染（不再裁切百分比）
  bsImg = pdfToCroppedBase64(pdfPath, FULL_PAGE, 200, bsPage)
  isImg = pdfToCroppedBase64(pdfPath, FULL_PAGE, 200, isPage)
} else {
  layout = "landscape-crop"             // 横向或单页，沿用旧逻辑
  // 原 BS_CROP/IS_CROP 百分比裁切（但已修单位换算）
}
```

页码定位策略：先验 `{bsPage: 1, isPage: 2}`（按《企业会计准则》列报顺序）+
逐页小图分类器（DPI 72，最多扫 8 页）修正；分类器失败保留先验，绝不中断。
分类器 prompt 极短："只回 A=资产负债表 / B=利润表 / C=现金流量表 / D=其他"。

`AiAnalyzeResult` 与 `/api/runs/:id/ai-analyze` 响应新增 `layout` / `pages` 字段，便于诊断。

### 修复 3：IS prompt 与字段集合

```ts
export const IS_FIELDS = [
  "revenue",
  "profit_before_tax",   // ← 新增
  "interest_expense",    // ← 新增
  "ebit",
] as const;
```

`buildIsSystemPrompt` 重写字段识别段落：

- 加「易混行项目」表格（rev/EBIT/PBT/IE 一一对应正反例）
- 明确 ebit **不是**原始行项目；模型优先如实返回 PBT + 利息费用，
  由系统按恒等式 `EBIT = 利润总额 + 利息费用` 推导
- 加勾稽自检（三、利润总额 ≈ 二、营业利润 + 营业外收入 − 营业外支出 等）

`callMultimodalIs` 默认白名单改用 `[...IS_FIELDS]`；
`callMultimodalSplitModel` 改为只要某张表需要任意 1 个字段，就下发整张表全部字段
（不污染 m4_map 的选择逻辑，因为 step 8 会按 `requestedFields` 过滤）。

### 修复 4：路由层恒等推导加固

`app/api/runs/[runId]/ai-analyze/route.ts`：

1. 统一取值器 `pick(k)` 改为先查 `extractedFields[k` 再查**未过滤**的 `rawByKey`
   （旧实现只看 `finalSuggestions`，请求 ebit 时永远找不到 PBT）
2. 新增**反向推导**：只缺 `profit_before_tax` 时由 `EBIT − 利息费用` 反解
3. 新增 **EBIT 恒等校正**：AI 常把「财务费用」/「营业利润」等任意行当 ebit 返回，
   当 AI 读数与恒等式偏差 >5% 且绝对差 >100 时，以恒等式为准覆盖，原值保留在 evidence。
   拦截了统一模式下「财务费用 964,656.73」被错当成 ebit 的实际案例（与真值 10,335,985.52 差 11 倍）
4. `app/api/analyze/route.ts` 补 `maxDuration = 180`（原缺失，流水线 3 次 OCR 约 90s 有超时风险）

### 修复 5：Python 流水线 OCR 关键字段校验重试

`zscore_pipeline/m2_extract.py` 新增 `_ocr_with_verification()`：

- `config.GLM_OCR` 新增 `verify_attempts: 3`、`verify_fields`
- OCR 后校验关键字段是否齐备，缺失则重跑（最多 2 次额外）
- 只把「本次能补上缺失字段」的行并入已有结果（不污染已抓到的字段，避免搅乱 m4_map 的「最晚页候选」选择）
- `verify_fields` 选取原则：
  - ✗ `retained_earnings`：CAS 下走 L2 组件，`match_field` 永不命中 → 空转重试
  - ✗ `interest_expense`：部分报表不单独披露，缺失时 m4_map 有兜底
  - ✓ 7 项：`revenue / profit_before_tax / current_assets / current_liabilities / total_assets / total_liabilities / equity_total`

诊断日志输出到 stderr（不污染 stdout JSON）。

